# Floptle v0.8.0 — "All Thumbs"

Controllers work. That's the headline, and it's a bigger sentence than it
sounds, because the engine had **no gamepad support at all** — scripts polled
`input.key("w")` against raw winit events, and `floptle-input` was an
eleven-line stub next to a design document nobody had implemented.

This release implements it: a named **action map**, gamepads with hot-plug,
per-player device slots for same-couch versus, and a fighting-game input layer
(buffering, motion inputs, SOCD) built into the engine because a script can't
reconstruct one correctly. One controller script now runs on a keyboard, on a
pad, or on both at once, and the player can rebind any of it.

The shipped default scripts are all converted, so a fresh project plays with
either device from the first frame.

> [ADR-0024](../decisions/0024-input-action-map.md)

## What an "action" is

Your script asks for a name. The Settings tab decides what triggers it.

```lua
if input.justPressed("Jump") then node.vy = 9 end
local x, y = input.axis2("Move")        -- WASD or the left stick, identical
```

`Jump` might be Space *and* the pad's South button — any binding fires it. The
script never asks which device you're on, and never has to change when someone
rebinds. That's the whole idea; everything below follows from it.

The full Lua surface:

| Call | What it gives you |
|---|---|
| `input.action(n)` | held right now |
| `input.justPressed(n)` / `input.justReleased(n)` | the edges |
| `input.heldSecs(n)` | seconds held — hold-to-charge with no timer of your own |
| `input.axis1(n)` | a trigger, the wheel, or a key pair, in −1..1 |
| `input.axis2(n)` | a stick or WASD as `x, y`, deadzoned and clamped |
| `input.player(n)` | the same API bound to another local player |
| `input.pushContext(n, opts)` / `popContext(n)` | layers that swallow input |
| `input.actions()` / `bindingsOf(n)` / `startRebind(n)` | build an in-game controls screen |

## One axis, two devices, honestly

A mouse and a stick are not the same kind of signal, and pretending otherwise
is why "gamepad support" usually means a second code path. Two things fix it:

- **Gate.** The `Look` axis's mouse half requires the right button held — a free
  cursor must never spin the view — while its stick half is ungated, because a
  stick recentres itself. One axis, no device checks in the script.
- **Rate.** A stick reports a *position* you integrate into a turn; a mouse
  reports a *displacement* that already is the turn. The mouse binding now
  reports pixels-per-second, so `yaw = yaw - lookX * dt` is correct on both —
  and frame-rate independent. 120 px moved over one 30 fps frame and 15 px over
  each of eight 240 fps frames produce the same turn, to within 1e-5.

## The fighting-game layer

The design doc listed combos and buffers as out of scope: "a game builds them in
script." That was right for a generic action layer and wrong for this engine's
next game. Buffering and motion recognition need a per-tick **history ring**,
and Lua can't rebuild one that survives a rollback replay.

So `floptle-input::history` keeps 180 ticks per player:

```lua
-- a special: motion first, so qcf+P never comes out as a bare punch
if input.motion("qcf") and input.buffered("Punch", 4) then
  input.consume("Punch", 4)          -- spend it, so it fires ONCE
  fireball()
end
```

- **Input buffer** — `buffered(name, ticks)` answers "pressed within the last N
  ticks and not yet consumed". A punch hit two frames before recovery ends still
  lands. Without `consume`, a 4-tick buffer would fire the attack four times.
- **Motions** — `qcf` `qcb` `dp` `rdp` `hcf` `hcb` `dd` `ff` `bb` `chargeF`
  `chargeU` ship seeded. Matching walks the ring backwards and requires every
  listed direction *in order*, so `2, 6` with no diagonal is not a quarter
  circle. Windows are counted in **ticks**, so a player on 144 Hz and one on
  60 Hz get identical leniency.
- **`setFacing(-1)`** mirrors directions after a cross-up, so `qcf` keeps
  meaning "toward the opponent". The engine has no opinion about who faces
  where; the game sets it.
- **SOCD** — what happens when ← and → are held at once, which a leverless
  controller does trivially. `Neutral` cancels (the tournament standard, and the
  default); `Last wins` lets a player pivot with no neutral frame.

All of it reads the **tick** domain — call it from `fixedUpdate`.

`assets/scripts/fighter.lua` is a worked example: walk, jump, normals, a
quarter-circle special, and local versus off a single script.

## Two players, one script

```lua
defaults = { player = 1 }
local me = input.player(params.player)   -- 1-based
if me.justPressed("Punch") then ... end
```

Pad slots are claimed by device **UUID**, so a player whose battery dies
mid-match returns to their own character on replug instead of everyone being
renumbered. An unplugged pad reads neutral rather than freezing its last pose.

## The Settings tab

Project Settings was a fixed 430 px modal with four topics stacked in a column.
It's now a **dock tab** — drag it anywhere, split it beside the viewport, close
it. It isn't in the default layout; Edit ▸ Project Settings creates or focuses
it.

- **Nav on the left, one section on the right** (Game, Rendering, Layers,
  Input), so each topic is short enough to read.
- **Search spans every section.** Type "gamepad", "deadzone", "raycast" or
  "retro" and it lands on the right one, instead of you having to know which
  topic owns a setting.

### The Input section explains itself

- **The action list is scanned out of your scripts.** Every action, axis and
  motion your Lua references, deduped, with the first `file:line` on hover. Add
  `input.action("Grapple")` to a script and it appears here, flagged ▲ because
  nothing is bound to it yet — which is exactly what a control that silently
  does nothing looks like.
- **Each row states the Lua call that reads it**, on hover. That's the missing
  link between this screen and your code.
- **Bind two ways.** `+` arms press-to-bind — press the key, mouse button or pad
  control you want; Escape always cancels. `▾` opens a **picker** listing every
  key (grouped), mouse button, pad button and pad axis, which needs **no
  hardware connected at all** — laying out controller bindings on a laptop is
  entirely normal.
- **A row bound only on the keyboard says so.** That's the failure that
  otherwise ships: a control that works for you and not for someone on a pad.
- **A LIVE strip** lights up as you mash, without entering Play.
- **"Fill in the standard ones"** adds Move / Look / Jump / Fire / Interact /
  Sprint / Crouch / Pause and friends, each bound on both device families. It
  only ever fills gaps — your own actions, bindings and SOCD choices are left
  exactly as they are.

## The default scripts are converted

`freelook`, `first_person`, `third_person`, `third_person_camera`, `character`
and `sword` all run on named actions now, on a keyboard, on a pad, or on both.
A new project seeds the matching `input.ron` alongside them.

| Was | Now |
|---|---|
| `input.key("w")` ×4, hand-normalised | `input.axis2("Move")` |
| `input.button(1)` + `input.mouse_delta()` | `input.axis2("Look")` |
| `input.pressed("space")` | `input.justPressed("Jump")` |
| `input.key("shift")` | `input.action("Sprint")` |
| `input.scroll()` | `input.axis1("Zoom")` |

Third-person's double-tap-to-run now triggers off the **Move axis leaving
rest**, so a stick flick arms it exactly like tapping W — it was key-edge-only
before and simply didn't exist on a pad.

Two tests guard this, because a drifting name means a brand-new project whose
camera silently cannot move: every name the shipped scripts reference must exist
in the starter map, and none of them may poll a raw device.

## Multiplayer: actions ride the wire

`NetInput` carried sorted key-name strings every tick. It now carries an action
bitmask plus axis values, and no keys at all. A pad player and a keyboard player
who press "Jump" produce byte-identical commands, so the one-script prediction
model holds across input devices — and the packet shrinks to three `u64`s.

**The cost, taken deliberately:** raw `input.key/pressed/released/button/clicked`
have nothing to replay from, so on a `Predicted` node they read **neutral in all
three places** — client predict, server authority, client replay. An unmigrated
controller visibly does nothing rather than quietly desyncing. Single-player
scripts are untouched, and the Input section lists every raw-key call site so
the migration has a worklist.

Because the wire indexes actions by their **position** in `input.ron`, the
handshake carries `InputMap::hash()` and refuses a mismatched peer. Personal
rebinds deliberately don't affect that hash, so rebinding never locks you out of
a session. `PROTO_VERSION` 8 → 9.

## Docking and undocking

`assembly.merge(node, other)` — the exact inverse of `assembly.split`. Two
compounds become one rigid body carrying their combined momentum, the absorbed
parts re-parent with their world pose kept, and the emptied root retires. A
docking latch, a crane taking its load, an in-space weld.

The join is perfectly **inelastic**: an off-centre catch spins the pair up
exactly as much as it should, and whatever relative motion is left at the
instant of the latch is felt as a jolt. Latching onto something anchored pins
the pair. Absorbed parts keep their entity ids, so per-part contact attribution
carries straight across the join.

`assembly.split` also takes a **prefab** now, so the half that comes away is a
live, scripted craft — an undocked lander that can fly home — instead of inert
debris.

## Fixes

- **Icons rendered as squares.** egui bundles only a subset of the emoji block,
  and 🎮 ⚠ ⚪ ✓ were not in it — nor were ⬢ ✏ ✨ 🎧 🖌, which had been tofu in
  the tab bar for some time. Every icon now lives in one module with a test
  asserting the real font stack can draw it. Tabs are ▦ Map, ⏱ Animating,
  ✱ Particles, ≣ Mixer, ◨ Paint.
- **Binding menus and the SOCD dropdown snapped shut when clicked.** Every
  action row built its picker from the same label, so all the rows' menus shared
  one egui widget id and fought over which was open. Rows are namespaced now.
- **The action map never loaded at boot.** It was wired into File ▸ Open only —
  which a launched build never goes through, so every exported game would have
  started with nothing bound.
- **The hidden multiplayer server ran with an empty map**, resolving every
  action to false while the client predicted a moving character.
- **`floptle --new` didn't seed `input.ron`** — the Hub's project-creation path,
  so Hub-made projects shipped the converted scripts with no map. Seeding moved
  to the shared path and `--migrate` tops up existing projects.
- **The Linux release build could not have compiled.** `gilrs` pulls
  `libudev-sys`, whose build script does an unconditional
  `pkg_config::find_library("libudev").unwrap()`. CI installed the X11, GL and
  ALSA headers but not `libudev-dev`.

## Housekeeping

Build output (`dist/`, `builds/`, `builds.zip` — 215 MB) is no longer tracked,
and `.gitignore` covers it along with agent scratch and root-level debug PNGs.
Existing history is unchanged; this only stops future churn.

## Known gaps

- **No gamepad has been tested against this build.** There was no controller on
  the development machine. The gilrs mapping is unit-tested (including the trap
  where gilrs calls L1 `LeftTrigger` and L2 `LeftTrigger2`), and the backend
  starts and pumps cleanly with zero pads — but nobody has pressed a physical
  button. `cargo run -p floptle-input --example pad_probe` prints slots, held
  actions and stick values.
- **The popup fix has no automated regression test.** egui reports a widget-id
  clash by *painting* over the offending widget, which doesn't happen in a
  headless pass; an attempt at a guard passed just as happily with the bug
  reintroduced, which is worse than no test. Verify popups by hand after
  touching row layout.
- **Input contexts** (`pushContext`/`popContext`) are implemented and unit
  tested, but nothing in the shipped scripts uses them yet.
- **Rebinding from a shipped game's settings menu** has the full Lua API and is
  covered by tests, but no example UI ships.
