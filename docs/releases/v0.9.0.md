# Floptle v0.9.0 — "Ground Truth"

Three bugs in this release had the same shape: the engine gave a confident wrong
answer and never said so. A node handle that reported the spawn position forever.
A texture filter that showed as `Pixelated` in the Inspector and reached nothing.
A script mistake that took the whole editor down with no error at all.

All three were found the expensive way — by an arcade fighter being built in the
engine, which spent days chasing the first one as a physics bug. Everything below
comes from that, plus the tools that would have found them sooner: frame-stepping,
hitboxes visible while you actually play, and animation timings baked from the
asset instead of guessed.

> Filed as floptle/0023–0028 in the task ledger.

## `me = node` no longer freezes at the spawn point

The most natural thing a script author writes:

```lua
function start(node)
  me = node        -- keep a handle so other functions can use it
end
```

`node_table` built a **fresh Lua table every hook**, with `x/y/z` as direct
fields copied from the transform at that instant. So `me` was a permanent
snapshot of the spawn pose. No error, no warning, no console output.

It failed in the most expensive possible way: **partially**. Everything using the
*passed* `node` — movement, ground probes, facing, impact effects — stayed
correct, so the character moved and animated perfectly. Only values read through
the stashed handle were wrong: hitboxes, cast points, the HUD's idea of where a
fighter was. The visible result was attacks passing through each other and spell
effects anchored to a spot on the floor where the round had started. It reads as
a physics bug, and it was chased as one.

It was asymmetric in a way nobody would guess, too. A handle to **another** node
(`find("Name")`, a `noderef` param) carries no raw fields, so every read goes
through the scene mirror and is live. `params.opponent.x` was correct while
`me.x` was stale — in the same function, on the same tick.

**Now** the engine builds one node table per script instance and re-stamps it
before every hook. A stashed handle is the same table the engine keeps updating.

A second, related edge is fixed with it: a **cross-script call that writes another
script's handle** — telling an opponent to reset and setting its position — used
to land after that script's read-back had drained, so the write was silently
dropped. The engine now records what it last stamped into a node table and drains
anything that differs before re-stamping. Physics moving a body between hooks is
correctly *not* mistaken for a script write, because the comparison is against
the table's own last-stamped values rather than the transform.

## A script mistake can no longer kill the editor

Passing a wrong table shape to `setMaterial` didn't produce a Console error. It
produced a `SIGABRT` and five coredumps in one evening, taking unsaved work with
it.

The cause was `panic = "abort"` in the release profile, and it was much broader
than the one bad call: **every** Lua error raised from a Rust callback killed a
release build — and `pcall` couldn't catch them either.

LuaJIT on x64 POSIX raises errors by real DWARF unwinding, which is exactly how
mlua turns a callback's `Err` into a Lua error. Under `abort`, every Rust frame is
compiled nounwind, so that unwind reached `panic_cannot_unwind` and the process
died. A wrong table shape was simply the easiest way to get there.

`cargo test` **silently ignores** a profile's `panic` setting, so no unit test
could ever have caught this, and the dev profile behaved perfectly throughout.
`crates/floptle-script/examples/error_path.rs` is the check that can — a release
binary that raises the error both inside and outside a `pcall`:

```
cargo run --release -p floptle-script --example error_path
```

Separately, a colour now accepts every spelling the docs promised: `{r,g,b}`
(which was documented, named in the converter's own error message, and the one
shape it refused), `{x,y,z}`, `{1, 0.5, 0.2}` and `vec3(…)`.

And `setMaterial` is now documented for what it is — a **setup-time** call that
inserts a component and queues a deferred write. Use `setShaderParam` for values
that change every frame.

## Texture filters actually reach the texture

A pixel-art HUD came out bilinear-blurred with `Pixelated` plainly selected in the
Inspector.

The Inspector stores a texture's filter under the path the Assets browser hands
it — **absolute**. Every renderer looks it up by the path the scene references —
**project-relative**. Permanent miss, silent fallback to the default. The setting
persisted, the Inspector kept showing it, and nothing ever read it.

This was never UI-specific: meshes, materials and the terrain palette were all
getting the default for any texture whose filter you set in the Inspector.

Settings are now canonically keyed project-relative, existing `textures.ron` files
migrate on load (so a project heals on next open — no re-picking), and changing a
filter re-uploads immediately instead of on reload. If you pre-scaled pixel art to
dodge this, you can go back to the authored resolution.

## Frame data you can actually tune

**Frame-step.** A fighter is authored in single frames: "is this jab 4 frames of
startup or 5" is the difference between a good move and a broken one, and it
cannot be answered by watching at full speed. Pause (⏸ / F2), then **⏭ Step**
(F3) advances exactly one gameplay tick — scripts, physics *and* animation each
moving one frame, so the pose belongs to the frame you stopped on. A tick counter
sits beside the button, so an observed event has a number you can put in a table.

While frozen, the tick accumulator drains each frame — unpausing can never
release a burst of caught-up ticks, and what you look at between steps is the
tick pose itself rather than an interpolated one.

`physics.step([n])` is the scriptable half, for a training mode's own stepper. It
freezes first if the game is running, since "advance one frame" only means
something from a standstill. Call it from `update`: the frame pass still runs
while the tick is frozen, and `fixedUpdate` by definition does not.

**Gizmos in the Game view.** `gizmo.*` shapes were Scene-view only — the right
default, since the Game view is meant to show what a player sees. But it meant
hit/hurtbox visualisation, the single most useful tool a fighting game has, was
invisible while you were actually playing with a controller in your hands. There
is now an "…also in Game view" toggle under Script gizmos in the ⏷ menu, off by
default and remembered between sessions.

## Animation events as data, not just callbacks

Clip events fired one way: the engine called a Lua function when playback crossed
one. That's right at runtime and useless as a *data source*, which is what an
animator wants them for.

The workflow is the correct one — scrub the attack, drop an event on the frame
where the strike visually connects, have the hitbox line up with it. What a
competitive fighter can't do is let that event **drive** the hitbox: events fire
off float playback time, stepped playback (`sample_fps`) quantises them to its
grid, clip time and gameplay frame disagree mid-crossfade, and a prediction replay
deliberately doesn't re-fire them.

So the authored list is now readable, and a game bakes it into integer frames once
at load:

```lua
local dur = anim:duration("Punch")
for _, e in ipairs(anim:events("Punch") or {}) do
  if e.func == "onHitboxStart" then
    move.startup = math.floor(e.t / dur * move.frames + 0.5)
  end
end
```

Both read the asset rather than playback, so they answer in `start()` before
anything has played a frame. Every machine loads the same `.anim.ron`, so the
baked numbers are identical everywhere and constant thereafter — deterministic and
rollback-safe, while the animator still authors by eye. Runtime dispatch is
unchanged; this is a read-only addition.

An unknown clip reads `nil`; a clip with no events reads an empty list, which is
deliberately a different answer.

## Two players, one keyboard

v0.8.0's action map let one script run on a keyboard or a pad. It did not let two
people share a keyboard, which is the default way an arcade fighter gets played.

Pads sort themselves out — `PadId::Any` resolves to each slot's own device. A
keyboard cannot, because there is only one of it: an unscoped `Key(KeyJ)` on
`Punch` punched for **both** fighters. The only way out was to duplicate the whole
action set under `Light2`-style names and branch on `params.player` in script,
which doubles the map, doubles what a settings screen renders, and makes
`input.player(n)` a half-truth.

A binding can now name a player:

```ron
Action(name: "Light", bindings: [
    Binding(source: Key(KeyJ),   player: Some(0)),      // P1
    Binding(source: Key(Digit1), player: Some(1)),      // P2
    Binding(source: Pad(id: Any, ctrl: Button(West))),  // either player's pad
]),
Axis2(name: "Move", socd: Neutral, bindings: [
    Keys(up: KeyW,    down: KeyS,       left: KeyA,       right: KeyD,       player: Some(0)),
    Keys(up: ArrowUp, down: ArrowDown,  left: ArrowLeft,  right: ArrowRight, player: Some(1)),
    Stick(id: Any, x: LeftStickX, y: LeftStickY, deadzone: 0.15),
]),
```

Omitted — the overwhelming default — means every player, so every existing
`input.ron` is unchanged and single-player is untouched. Right-click a binding
chip in Project Settings ▸ Input to scope it; scoped chips read `⌨ J  P1`. An
action with an unscoped **keyboard** binding in a `players > 1` project is flagged
▲, because "both characters jump off one press" is otherwise found by watching it
happen.

The scope lives on the **binding**, never the action. The action list is what the
netcode indexes positionally and what `InputMap::hash()` covers, so scoping a
binding cannot invalidate a live session.

It also repairs motions for player 2. `dir()`, `dirHeldTicks` and every motion
read one map-level axis, resolved per player — so one `Move` axis carrying WASD
for P1 and the arrows for P2 gives each of them their own quarter-circle. Two
separate axes never could: the recogniser read player 1's for everyone, silently.
That was costing a game the engine's motion recogniser, which is precisely the
part a script can't rebuild correctly under rollback.

## Housekeeping

`cargo run -p floptle-input --example parse_map -- <project>/input.ron` parses a
real map, prints what it holds, and checks it round-trips — a fast way to confirm
a project still loads after a schema change or a hand edit.

## Known gaps

- **Still no gamepad has been tested against a Floptle build.** There is no
  controller on the development machine. The mapping is unit-tested and the
  backend pumps cleanly with zero pads, but nobody has pressed a physical button.
  `cargo run -p floptle-input --example pad_probe`.
- **Rollback netcode is not here.** A fighter needs both players simulated locally
  every tick with snapshot/restore across a mispredict; today's `Predicted (owner)`
  mode plus interpolation-delayed remotes cannot carry a 5-frame parry window. It
  is the next large piece of work, tracked as floptle/0022.
- **Stepping backwards** one tick isn't implemented. It essentially falls out of
  rollback's snapshot/restore, so it's sequenced after it.
