# Floptle v0.21.2 — "Update Yourself"

The Hub can update itself now. Until this release it could not, and it never
said so.

## What was actually wrong

The Hub has installed engine versions since v0.7.0, but it had no way to install
**itself**. Two separate gaps, and either one alone would have been enough:

- `releases.json` carried only *engine* bundles. The `floptle-hub-*` archives
  were built and uploaded to every release, but no URL and no checksum for them
  existed anywhere a program could read. The Hub had nothing to download even if
  it had wanted to.
- Nothing ever compared the running version to the newest one. `About` printed
  `version 0.21.1` and stopped — a fact you can't act on, because it only means
  something next to the version that exists.

So updating meant noticing a release had happened, finding the right archive for
your platform on GitHub, and replacing the binary by hand. Most people would
simply never have done it.

## Update and restart

One button. It downloads the Hub's own bundle, checks the SHA-256, puts the new
binary where the running one is, and reopens the Hub.

Replacing a running executable is the only awkward part, and the trick is that
**a running binary can be renamed even where it cannot be deleted** — Windows
refuses to delete one and permits moving it; on Unix a rename repoints the
directory entry while the running process keeps its inode. So the swap is two
renames, the same on every platform, and the leftover is deleted at the next
launch when nothing has it open.

If the second rename fails, the first is undone. A Hub that moved itself aside
and then failed to land the replacement is the one outcome nobody could recover
from inside the app, so it is the case with the most care spent on it.

**It can legitimately be impossible**, and then it says so instead of offering a
button that would fail. A Hub in `/usr/local/bin` or on a read-only mount cannot
rewrite itself without privileges this app deliberately never asks for; you get
the reason and a download link. That check runs *before* the button is drawn —
finding out after a 6 MB download is a worse way to learn it.

## Being out of date is now unmissable

Three levels, on purpose:

- **A banner**, on launch. "Later" puts it away **for this session only** — it
  is back next time you open the Hub. The engine banner remembers a dismissal
  per version, which is right for "there is a newer engine you may or may not
  want"; it is wrong for "the app you are using is old", where one idle click
  would silence it forever.
- **A chip in the tab bar** that cannot be dismissed at all and stays until the
  update is actually installed. It covers the engine too, when that is what's
  behind — the Hub outranks it, because an old Hub is what would stop you fixing
  the other one.
- **The About tab** answers the question directly: *This is the newest Hub*, or
  the new version with its release notes and the button.

## Upgrading — this one time, by hand

A Hub at v0.21.1 or older has none of this code and cannot see the update, so
**download v0.21.2 from the releases page once**. Every release after this one is
a single click from inside the Hub.

`cargo test --workspace` and `cargo clippy --workspace --all-targets` are both
clean.
