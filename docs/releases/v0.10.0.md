# Floptle v0.10.0 — "Same Fight"

Floptle has had multiplayer since v0.5: one machine simulates, the others watch
a slightly delayed copy and predict their own avatar. That is the right shape
for almost every game, and the wrong shape for exactly one — a fighting game,
where the decision you make is made against your opponent's exact state *this
frame*, and where a correction that nudges your character 40 ms later is the
difference between a punish and a whiff.

This release adds the third mode. **Rollback**: every peer simulates every
fighter, every tick, from the same inputs. Nothing about a hit ever crosses the
wire — only button presses do — so both machines agree about hitstop, meter and
trades because the *simulation* agrees, not because they negotiated.

Around it is the rest of what a netcode needs before you can ship something
with it: a dedicated server, interest management for player counts, replays,
a referee, and real per-player ping.

> ⚠ **The wire protocol went from 9 to 11.** Builds refuse mismatched versions
> at connect, so every machine in a session needs updating together.

---

## Rollback netcode

Set a node's **🌐 Networked ▸ mode** to **Rollback (all peers)** and every
machine runs it. The engine handles input delay (a fixed 2 ticks, chosen once
per session because how a game *feels* must not change mid-match), predicts a
missing input by repeating the last one, and — when the guess turns out
wrong — restores the last agreed tick and re-simulates everything since, with
no rendering in between.

Your side of the contract is two functions:

```lua
function snapshot()   return { state = state, frame = frame, health = health } end
function restore(s)   state, frame, health = s.state, s.frame, s.health end
```

That's the whole opt-in. Transforms and physics bodies are saved for you.

**Anything you leave out of `snapshot()` survives the rewind unchanged**, and
that is precisely what a desync is made of. Nothing warns you at the moment you
forget — the match keeps playing and the two machines quietly stop agreeing
about one counter. Which is why:

**Checksums are mandatory and always on.** Every 30 confirmed ticks each peer
hashes its state and the host compares. A mismatch is loud: a Console error
naming the tick, red in the 🌐 panel, and `net.on("desync")` so a match can end
honestly instead of playing out as two different fights. A rollback
implementation without this doesn't fail loudly; it plays a subtly different
match on each screen until someone notices the health bars disagree.

Past a depth cap of 8 ticks the simulation **stalls** rather than guessing
further — the game runs slightly slow instead of teleporting the opponent, and
recovers on its own. `net.stalled()` lets you put your own banner on it, which
matters because a stall is otherwise indistinguishable from a bad frame rate.

New Lua: `net.random` (drawn from the match seed, tick and draw index, so every
peer rolls the same number *and* a re-simulated tick rolls it again),
`net.replaying`, `net.stalled`, `net.inputDelay`, `net.rollbackDepth` /
`Max` / `Average`, `net.mispredictRate`, and `node.tickPos` / `node.tickYaw`
for reading and writing the simulation pose rather than the interpolated one
the camera renders.

Full guide: **[docs/multiplayer.md](../multiplayer.md)**.

## The referee, and replays

Both are the same idea and share one implementation: a second, headless
simulation of the match on the host, advanced by the same driver.

The **referee** only ever advances to ticks every peer's input has actually
arrived for. It never guesses and never rolls back, so it is never wrong — only
behind. Every peer's checksum is judged against it rather than against a quorum
of the other players, and that is the difference between knowing "someone is out
of sync" and knowing "**that machine** is". A room full of clients running the
same modified build agrees with itself perfectly.

**Replays** are the same second world with a different stopping rule. A rollback
match is a pure function of (scene, seed, input delay, roster, inputs), so the
input log *is* the match: a full set is kilobytes, and playing it back
re-simulates rather than re-enacts. Every match writes one to `replays/` in your
project; the 🌐 panel lists them. A desync that reproduces in a replay is a
desync you can debug at your leisure instead of chasing live.

## A dedicated server

```
floptle-runtime --server <project-dir> [--scene …] [--port N | --relay host:port]
                [--tick 60] [--interest 150] [--budget 16384]
```

The same `World`, the same physics, the same scripts, the same session the
editor hosts — minus the window, the GPU, the audio and the input, because
nobody is sitting at it. Until now every session was hosted by a player's game,
which is fine for friends-and-a-lobby-code and wrong for anything that has to
stay up: the world ends when the host closes their laptop, and the host is also
a player with an unfair zero-latency view of it.

It **refuses a `Rollback` scene**, which is a design position rather than a gap.
A rollback match has every peer simulating every tick, so its "host" is a
referee and a relay rather than a simulation — and for a fighting game that role
is one of the players.

## Interest management

The player-count feature, off by default:

```lua
net.host{ interest = 150, interestBudget = 16384 }   -- metres, bytes/sec
```

Each client is told about its own neighbourhood instead of the whole world,
inside a per-client byte budget. Relevance decides what a client *may* hear
about; a priority accumulator decides what it hears *this snapshot*, spending
the budget nearest-and-busiest-first.

**Nothing is dropped — only deferred.** Everything that loses a turn accrues
priority and wins a later one, which is what makes the feature safe to switch on
without auditing a game for things that must never be missed. For the few that
genuinely must arrive from anywhere — a match clock, an objective, a boss —
there's an **always relevant** checkbox on the Networked component.

One refinement over the design: an entity leaving a client's set *despawns*
there only if it was a runtime spawn. Scene-authored nodes just go quiet,
because the client already has them from its own scene file and the server has
no ron to send back — despawning one would remove it for good.

## Per-player ping that's true through a relay

The 🌐 panel reported the transport's RTT as the player's ping. Through a relay
the transport only ever sees its own leg, so what it was actually reporting was
host↔relay: off by a whole hop, and always in the flattering direction. Ping is
now probed end to end at the application level, per player.

## Also in this release

- **A dev-only link impairment knob.** `FLOPTLE_NET_IMPAIR=50ms,2%` adds
  latency and loss to this build's *real* transports, so a rollback match can be
  rehearsed at match conditions between two instances on one desk. The panel
  section doesn't exist without the environment variable, so a real session can
  never be silently degraded from the UI. Reliable traffic is never dropped — a
  real reliable channel retransmits, and dropping handshakes would only invent
  failures the field can't produce.

- **Authority snapshots stop at the driver's door.** With a rollback driver
  live, the host's snapshots no longer apply to the nodes it is driving — the
  guard is at *application* rather than gathering, so the window before the
  match starts keeps working normally.

- **The join seam**, where two blocking bugs lived: a tick could be sampled
  twice while stalled (a straight desync), and a joining client's fighters were
  parked by the client-side setup pass and stood still all match.

- **The whole rollback Lua surface now exists in the engine's own script
  editor**, not only in the VSCode stub library. It had shipped in one and not
  the other, so a developer who set a node to Rollback in the Inspector couldn't
  discover a single call the mode requires. There's now a test that fails if the
  two surfaces drift again.

- **Interest management is visible while it runs.** It is the one feature whose
  job is to *not* send things, so with no readout it was indistinguishable from
  a bug. The panel shows, per client, how much of the world it's being told
  about and how much is waiting for a turn.

- **[docs/multiplayer.md](../multiplayer.md)** — the missing half of the
  documentation. The design docs said why it works; nothing said how to build
  with it. It goes from a single-player scene to two machines and ends at
  shipping, and it opens by picking the replication mode, which is the one
  decision here that's expensive to change later.

## Known limits

- **Cross-platform determinism** (x64 ↔ Apple Silicon) is expected, not proven.
  IEEE add/mul/div/sqrt are bit-exact everywhere; the risk is `sin`/`cos`/`pow`,
  which may differ in the last bit between platform math libraries. A fighter's
  simulation path typically avoids them.
- **Bodies in solver-resolved contact** are out of scope for rollback — that's
  what the Rigidbody's **pushbox only** switch is for.
- The two-machine acceptance run over a real relay at 60–120 ms is still
  outstanding; the checklist for it is in
  [docs/rollback-p7-fofighter-checklist.md](../rollback-p7-fofighter-checklist.md).
