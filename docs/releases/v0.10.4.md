# Floptle v0.10.4

**A regression fix. 0.10.3 broke rollback matches after exactly one tick.**
Wire protocol unchanged (12) — this interoperates with 0.10.3.

If you are on 0.10.3 and running rollback, take this one.

## The driver fell out of the editor at the end of its own first tick

`net_rollback_tick` takes the driver out of the `Editor` so it can borrow the
world, the physics sim and the script host at the same time, then puts it back
at the end. 0.10.3 added a deferred script audit near the bottom of that
function and wrote it as a *second* `take()` — which found `None`, because the
first one still held the driver. The single restore that used to sit there went
away in the same edit.

So every rollback tick ran once and then dropped its own driver. From the next
tick on, `net_rollback.is_none()` and the whole path is skipped — while the
fighters keep their place in the script filters, because nothing tore those
down. Nothing ran them again for the rest of the match.

Every symptom follows from that one line:

- **The fighters tick exactly once.** The game side's telemetry read `f=1` on
  both machines — one `fixedUpdate` and never another. That single digit is the
  whole diagnosis.
- **Both machines, identically.** It is not a host/client asymmetry; it is the
  tick function, which both run.
- **`stalled=false depth=0` forever.** `RollbackInfo` is published from inside a
  simulated tick, so with no ticks running it freezes at whatever tick 1 left.
  The telemetry was not lying about the network — it was reporting a number that
  had stopped being updated.
- **No script errors.** Nothing failed. Nothing ran.
- **Inputs kept flowing.** 0.10.3's actual fix is fine; the sessions still tick
  and the per-peer rings still work.

The restore is back, and the whole span from the `take` to it now has a single
exit. If you need to bail out in there, set a flag and bail *after* the restore.

## What caught it

0.10.3's new orphan detector, on its first live run, on both machines:

```
🥊 2 Rollback node(s) are being run by NOTHING this match — not the rollback
   driver and not the global script passes: Player1, Player2.
```

That check exists because floptle/0039's second symptom was a match freezing
with a clean console. It named the fault correctly the first time it met one —
including one I had just written — which is the argument for that class of
check in general: an invariant worth stating is worth stating out loud at
runtime, because the thing that violates it next may well be your own fix.

## Two tests, because the class matters more than the line

- **`the_rollback_tick_always_puts_its_driver_back`** — a source check, since
  the failure needs a live `Editor` and produces silence rather than a crash. It
  asserts one `take`, one restore, and no `return` between them. Verified
  against the 0.10.3 source: it fails there.
- **`the_client_join_sequence_leaves_no_rollback_node_unrun`** — the regression
  test the field report asked for. It walks the join sequence (scene switch →
  `plan_client_side` with an empty rollback set → the driver's rebind), asserts
  the un-driven window between them is real, asserts it closes, and asserts a
  driver that vanishes is detectable.

The orphan check's predicate is now a free function
(`orphaned_rollback_nodes`), following `plan_client_side`'s precedent, so the
sequence can be driven in a test at all.
