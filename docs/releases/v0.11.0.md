# Floptle v0.11.0

**Export a build for any platform, from any platform.** Windows from Linux,
Linux from a Mac, macOS from Windows — in about two seconds, with no compiler,
no cross-toolchain, and no engine source checkout.

## Exporting stopped compiling the engine

Export Game… used to shell out to `cargo build --release --target …`. That
carried three costs, and the third one was fatal:

- it needed a C cross-toolchain (mingw for Windows) installed by hand;
- it needed the **engine source checkout the editor was built from**;
- macOS was impossible — Apple's SDK can't leave a Mac — so that target made you
  run a GitHub workflow yourself and drop the artifact in `prebuilt/`.

The second one is the fatal one. A Hub-installed editor's compiled-in source
path is the CI runner's (`/home/runner/work/Floptle/…`), which exists on no
user's machine. So **cross-platform export could never work from a Hub install**
— the ordinary way to run the engine. It failed before it ever looked for a
compiler, and the error talked about a checkout rather than about that.

The fix is to notice that there was nothing to compile in the first place.

An exported build is *the engine binary + your assets + a `floptle-game.ron`
manifest*. **Nothing about a project is compiled in.** So the binary a build
needs is not something to produce — it is something to *fetch*, and it is
byte-for-byte the bundle the release pipeline already publishes for that
platform and the Hub already installs to run the editor.

So the export downloads it. Once, checksum-verified against the same
`releases.json` the Hub reads, cached under
`<data-dir>/templates/<version>/<platform>/` beside the Hub's installed
versions. First export of a platform: a few seconds. Every one after: instant.

This is Godot's model (export templates) and Unity's (build support modules).
Unreal is the one that really compiles per target, and it is the one everybody
complains about.

Measured on the machine this was written on — Linux, exporting for Windows:

```
first export   2.1 s   (download 38 MB, verify, unpack, stamp 465 assets)
cached export  0.05 s
```

A template is pinned to the editor's **own version** — it's part of the cache
key — because mixing them would ship a game whose wire protocol disagrees with
the editor that built it.

`floptle-dist` is a new crate holding the manifest types and the
download/verify/unpack path, shared by the Hub and the editor. A template and an
installed engine are the same artifact; now they are also the same code.

### Source checkouts still build

Running from a checkout at a version with no published bundles — engine
development between a version bump and its release — falls back to
`cargo build --target …` and says so in the status line. That is the only
remaining use of the compiler path. macOS has no fallback, and needs none: every
released version has a macOS template.

## Three ways a successful export shipped a broken game

Found by exporting a real project and running it, which is how all three had
been surviving.

**Absolute asset paths rode along.** `resolve_asset_path` returns an absolute
path as-is — no existence check, no rescue — so a build carrying one works only
on the machine that exported it, and fails *silently*, because a model that
doesn't load simply isn't there. One real project shipped 27 files (every
animation, both character models) pointing at `/home/<user>/…`. Paths into the
project are now rewritten to project-relative automatically; paths outside it
can't be repaired — the file isn't in the build — so they're reported as a
warning naming each one.

**The developer's save file shipped.** The engine writes `save/` (Lua
`save.set`) and `replays/` into the project. A build carrying the developer's
copies hands every player a pre-populated save: in the field this made a build
boot straight into a match instead of its own menu. Both are now excluded — at
the project root only, since a nested `save/` is content.

**A bad entry scene fell back silently.** `project.ron`'s `entry_scene` wanted a
path (`scenes/menu.ron`) while Lua `scene.load` takes a bare name (`menu`). Two
conventions for naming one scene. A perfectly reasonable `entry_scene: "menu"`
resolved to nothing and fell through to `scenes/first.ron` with an stderr line
nobody sees — **so the scene you playtested was not the scene that shipped**.
Both spellings now resolve, in the editor and in a build, and an entry scene
that resolves to nothing fails the export instead of shipping a build that boots
somewhere else.

## Also

- **Headless export**, so builds are scriptable and CI can prove this works:
  `floptle --export <PROJECT> <OUT> <PLATFORM> [TITLE]`, where `PLATFORM` is
  `host` or a release key (`windows-x86_64`, `macos-aarch64`, …). Same code the
  dialog runs.
- An exported game printed `Floptle editor v0.11.0` on startup. It now prints
  its own title.
- Export moved out of `main.rs` into `editor/src/export.rs`.
- 894 tests (10 covering export alone, each of the three shipping bugs among
  them), workspace clippy clean.

## Upgrading

Nothing to do. The first export for a given platform fetches its template; after
that it's cached. If you exported before, re-export — the build you have is
missing these fixes.
