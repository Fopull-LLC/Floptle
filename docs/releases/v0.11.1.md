# Floptle v0.11.1

**A rollback node never got a `lateUpdate`.** Reported from the field by the
Fofighter team as floptle/0042, diagnosed against the source rather than a log —
because this fault produces no log at all.

## Two of the three passes had a substitute. The third had none.

Claiming a node put it in `script_skip`, and `run_pass` honours that set for
**every** pass. But the rollback driver replays exactly two things per tick:

| pass | global | substitute for a driven node |
|---|---|---|
| `fixedUpdate` | skipped | `run_fixed_for`, per replayed tick |
| `update` | skipped | `run_frame_for`, on the tick clock |
| `lateUpdate` | **skipped** | **nothing** |

`script_skip`'s own doc-comment states the invariant this broke: *"True means
SOMETHING else has taken responsibility for running it… and if nothing has, its
scripts never run at all, which is a failure with no symptom other than
silence."* For the late pass, nothing had.

It fails in the most expensive way available. `lateUpdate` is documented as the
pass that runs *after physics and the interpolated writeback*, which makes it
the only correct place to write a node's cosmetic transform — anything written
from `fixedUpdate` gets overwritten by the writeback. So the docs send you
there, and going there silently stopped working the moment a node became a
Rollback node. **Offline it was perfect.** Every local test, every bot match,
the whole authoring loop. It broke only in a net match, with no error and no log
line. In the field it drew both fighters at the same yaw for an entire match
while every hitbox came out the correct way round.

## The two reasons for filtering were never the same reason

They had been sharing one set, and that is the actual bug:

- **A snapshot-driven node on a client** is not simulated locally at all. Its
  state arrives in snapshots. Skipping every pass is right.
- **A driver-owned node** *is* locally simulated — only the **scheduling** of its
  ticks moved into the driver. Its per-frame cosmetic pass has no reason to stop,
  and it must not be replayed either: a rollback frame runs many ticks, so
  replaying the late pass would fire it N times, which is worse than not running
  it at all.

So they are two sets now. `driver_skip` gates `fixedUpdate` and `update` and
leaves `lateUpdate` alone; `script_skip` keeps its old meaning exactly. The late
pass already runs once per rendered frame, after `writeback_interpolated` and
outside the tick loop — so separating the sets gets both timing guarantees for
free, rather than by adding a `run_late_for` that would have been wrong.

Both filter-planning paths were routed across: `plan_client_side` and
`net_apply_host_filters` each folded the driver's nodes back into the
all-passes set, so fixing the host in isolation would have changed nothing in
the field.

## Answering the question the report asked

Yes — velocity and position writes from `lateUpdate` are still drained for a
driven node. The drain right after `run_late` iterates whatever the pass wrote
and is entity-agnostic, so a driven node's late writes flow through unchanged
now that the pass fires for it.

## The detector could not have caught this, and now can

`net_rollback_check_orphans` asks *"does somebody run your ticks"* — and for
these nodes somebody did. The class was invisible to it.

Its new sibling asks *"does somebody run your passes"*: a node the driver owns
that also sits in the all-passes filter is now named in the Console, with what
it costs. The two reports don't double-count — an undriven node is an orphan and
is reported by the other check.

## Also

- 897 tests. The regression test was **verified to fail on the pre-fix code**,
  with the reported symptom: the `lateUpdate` counter never moves while the
  other two do.
- A companion test pins the case that must NOT change — a snapshot-driven node
  still skips every pass, `lateUpdate` included.
- Workspace clippy clean.

## Upgrading

Update both ends of a match. Fofighter's workaround — moving the fighter's
cosmetic pass onto the tick clock — can come back off; it worked only because
that body has `lock_rot` all-false and no `align_up`, and it was never general:
a game needing the *position* half of `lateUpdate` had nowhere to go.
