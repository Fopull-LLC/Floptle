# Floptle v0.21.0 — "Who's Playing"

A game can ask who is sitting in front of it.

## `account.*`

```lua
account.signIn()          -- returns immediately; they approve in a browser
account.state()           -- "signedOut" | "starting" | "waiting" | "signedIn" | "failed"
account.code()            -- while waiting: { code = "WXYZ-9999", url = "…", expiresIn }
account.player()          -- when signed in: { id, name, email, tier }
account.error()  account.cancel()  account.signOut()

account.get("/wallet", function(res) end)
account.post("/games/mygame/events", { event = "boss_killed", event_id = id }, cb)
account.put("/games/mygame/saves/slot1", { data = t }, cb)
account.delete("/games/mygame/saves/slot1", cb)
```

Foverse accounts, Fobucks, cloud saves, leaderboards and missions — from Lua,
in the editor and in an exported build, with or without the Hub installed.

**Why this is Rust and not Lua** is one line long: the provider mandates PKCE
S256 and a Lua script has no SHA-256. The previous answer on the books was to
hand the Hub's token to the running game. That was worse: it needs the Hub
installed, it needs a game to have been launched *from* the Hub, and it puts a
live access token where a script can read it. Doing the flow natively costs one
dependency and covers every case.

So **a script asks for a player, never a token.** There is no `account.token()`
and there will not be: a shipped game's Lua is readable, and anything a script
can hold, somebody can read out of the file and post somewhere else. The token
stays in Rust and is attached to requests there — which is also why the calls
take a **path** rather than a URL. There is exactly one host they can reach, and
that is the whole security model. A URL where a path belongs raises at the call
site with the reason, rather than arriving three frames later as `res.error`
that reads like the server refused it.

**Polled, not called back.** Signing in takes as long as a person takes to pick
up their phone and open a browser. A sign-in screen is redrawing every frame
anyway, so `state()` reports where the flow got to and a callback for something
that can sit at "waiting" for a minute never has to exist.

**One session, everywhere.** It lives in the OS keyring, in the same entry the
Hub uses — sign in from the Hub and your game already knows the player, sign in
from a game and the Hub does. Stop and `scene.load` drop pending callbacks and
abandon an unfinished sign-in; the session survives, because nobody should have
to sign in again for pressing Play twice.

**Nothing happens until it is asked for.** `account.state()` answers
`"signedOut"` for a signed-out player without constructing anything — a project
that never signs anybody in never reads the keyring, and never trips an "an app
wants your passwords" prompt on a player who only wanted to play the game.

The device flow itself is not new code: it is the Hub's, which has been signing
in to fopull.com correctly since Phase 1, moved to a new `floptle-account` crate
that both now share. `floptle-hub::auth` re-exports it, so the Hub is unchanged.

## The rule this exists to enforce

Floptle Cloud has missions and a Fobucks wallet, and **Fobucks are real** — they
buy real goods on fopull.com. So the wallet is read-only and there is no route
that credits it. A game reports what *happened* and the server owns the rule
that turns it into money:

```lua
account.post("/games/mygame/events", {
  event = "boss_killed", count = 1,
  event_id = playerId .. ":boss:" .. n,   -- REQUIRED; makes the report idempotent
}, function(res) end)
```

A modified build can lie about the event. It cannot invent the amount, claim a
`once` mission twice, or write the balance. [`docs/web-api.md`](../web-api.md)
has the three answers that surprise a first test — `event_id` is mandatory, an
empty `awarded` is not always a failure, and a mission pays nothing until it is
approved.

## The wireframe no longer dims when you stand inside a room

v0.20.0's new depth cue asks, per edge, *does any face using this point at the
camera?* Inside a box it answers **"all of it"** — and building a box and
standing in it is the commonest position there is in map editing, so the whole
wireframe went faint at once. The answer was true and useless: the only faces
that could hide anything from you there are the ones behind the camera. Same for
the back of a one-sided plane.

Nothing facing you means nothing is in the way, so the cue steps aside and
everything draws at full strength. The distance fade is unaffected — it never
depended on which way a face pointed.

The test that should have caught this had documented the flaw as if it were the
intent, asserting that nothing reads as visible from in there. It now asserts
the opposite, with a one-sided plane case beside it.
